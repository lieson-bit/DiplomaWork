# Order Service Microservice - Complete System Description

## 📋 **Service Overview**

The **Order Service** is a critical microservice in a delivery platform that manages the entire lifecycle of delivery orders - from creation to completion. It handles order management, driver assignment, real-time tracking, payments, messaging, and route optimization.

## 🎯 **Primary Functions**

### 1. **Order Management**
- Receive orders from customer booking form with complete order structure
- Store order details in database (pickup/delivery addresses, package details, pricing)
- Track order status through 5-step workflow
- Maintain order history with timestamps

### 2. **Capacity Management**
- Check driver's vehicle capacity before assigning orders
- Fetch vehicle max weight/volume from Driver Service API
- Calculate current load from active orders in database
- Prevent overloading by rejecting orders that exceed capacity
- Provide recommendations when capacity is exceeded

### 3. **Driver Acceptance Flow**
- Notify driver when new order is assigned (via in-memory notifications)
- Allow driver to accept or reject orders
- Process payment deduction from customer when driver accepts
- Add pending balance to driver's account
- Update order status from 'pending' to 'driver_assigned'

### 4. **Status Tracking (5-Step Progress)**
```
Step 1: Order Placed (pending)
Step 2: Driver Assigned (driver_assigned) 
Step 3: Route to Pickup (route_to_pickup)
Step 4: In Transit (in_transit)
Step 5: Delivered (delivered)
```
- Driver updates status as they progress through delivery
- Each status change triggers notifications for customer
- Progress percentage calculated automatically (0%, 25%, 50%, 75%, 100%)
- Timestamps recorded for each milestone

### 5. **Payment System (Simple Balance-Based)**
- No external payment API integration
- Customer balance deducted when driver accepts order
- Driver receives pending balance on acceptance
- Pending balance released to available when order delivered
- Track weekly spending (customer) and earnings (driver)
- Maintain total earned/spent balances

### 6. **Route Optimization**
- Traveling Salesman Problem (TSP) algorithm implementation
- Optimizes delivery sequence for drivers with multiple orders
- Constraint: Pickup must come before delivery for each order
- Calculates shortest distance and estimated time
- Shows optimized route with labeled order sequence
- Calculates estimated savings vs non-optimized route

### 7. **Messaging System**
- Simple in-app text messaging between customer and driver
- Messages stored in database with timestamps
- Track read/unread status
- No real-time WebSocket - uses HTTP polling

### 8. **Rating System**
- Customer rates driver after delivery (1-5 stars)
- New rating formula: (current average + new rating) / 2
- Store individual ratings and calculate new average
- Optional review text

### 9. **Notification System**
- Simple in-memory notification queue (no WebSocket)
- UI polls for notifications every 5-10 seconds
- Notification types: order_created, order_accepted, status_update, new_message, new_rating
- Mark notifications as read

### 10. **Location Tracking**
- Store driver GPS coordinates during delivery
- Update order with current driver location
- Customers can view driver's real-time position on map
- Track complete route history for completed deliveries

## 🗄️ **Database Schema (8 Tables)**

### 1. **orders** - Main order table
- Order ID, number, customer/driver IDs
- Status tracking (pending → driver_assigned → route_to_pickup → in_transit → delivered)
- Pickup/delivery addresses with coordinates
- Package details (weight, volume, category)
- Driver and vehicle information
- Pricing and payment status
- Timestamps for each milestone
- Driver rating and customer review

### 2. **order_status_history** - Audit trail
- Records every status change
- Who changed it and when
- Previous and new status

### 3. **order_messages** - Communication
- Messages between customer and driver
- Sender type, content, timestamp
- Read/unread status

### 4. **user_balances** - Payment balances
- Available balance
- Pending balance
- Total earned (drivers) / spent (customers)
- Currency

### 5. **balance_transactions** - Transaction history
- Each payment, refund, adjustment
- Linked to orders
- Before/after balances

### 6. **driver_ratings** - Rating history
- Individual ratings per order
- Review text
- Calculates driver's average rating

### 7. **location_tracking** - GPS tracking
- Real-time driver coordinates
- Speed, bearing, accuracy
- Timestamp for each point

### 8. **driver_capacity_tracking** - Capacity monitoring
- Daily capacity utilization
- Weight and volume carried
- Efficiency scores

## 🔄 **Service Dependencies**

### External Services Called
- **Driver Service** (`http://localhost:3002`)
  - Endpoint: `GET /api/drivers/{id}/vehicles-picture`
  - Returns vehicle capacity (maxWeight, maxVolume)

### External Services That Call This Service
- **Customer Booking UI** - Creates orders via `/api/orders/receive`
- **Driver App** - Accepts/rejects orders, updates status

## 📊 **Order Workflow**

```
1. Customer submits order via UI
   ↓
2. Order Service receives order with driver pre-selected
   ↓
3. Capacity check: 
   - Fetch driver's vehicle capacity from Driver Service
   - Query active orders from database
   - Calculate if new order fits
   ↓
4. If capacity exceeded → Reject with recommendations
   ↓
5. If capacity OK → Save order to database (status: 'pending')
   ↓
6. Add notification for driver (polling endpoint)
   ↓
7. Driver sees notification, accepts/rejects
   ↓
8. If accepted:
   - Update status to 'driver_assigned'
   - Deduct payment from customer balance
   - Add pending balance to driver
   ↓
9. Driver updates status as they progress:
   - 'route_to_pickup' → Customer notified
   - 'in_transit' → Customer notified
   - 'delivered' → Release driver's pending balance
   ↓
10. Customer rates driver (1-5 stars)
    - New average = (old_avg + new_rating) / 2
```

## 🔐 **Authentication**

- **JWT Tokens** for customer/driver endpoints
- **Service Secret** (`x-service-secret` header) for service-to-service calls
- Tokens contain: userId, userType (customer/driver)

## ⚠️ **Important Notes**

1. **No WebSocket** - Uses HTTP polling for notifications
2. **Simple Payment** - No external payment API, balance-based only
3. **Capacity Check** - Requires Driver Service to be running
4. **Route Optimization** - Works with 2+ active orders per driver
5. **Notifications** - Stored in memory (lost on restart), UI polls every 5-10 seconds
